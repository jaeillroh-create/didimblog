# 디딤 블로그 인포그래픽 (규칙 v2)

완성된 블로그 본문에서 데이터를 골라 썸네일 1개 + 본문 인포그래픽 0~3개를 **설계 → 검사 → 렌더링 → 검수**한다.
기준 문서는 `references/rules-v2.md`(사용자와 합의한 v2)다. 백오피스 코드의 옛 규칙(`references/legacy-code-rules.md`)과 다르면 **v2를 따른다**.
브랜드·카테고리·CTA 공통 규칙은 **didim-blog-core 스킬을 함께 읽는다.**

## 절대원칙 (코어 스킬이 없어도 지킨다)

- 이미지 속 글자에 **연락처·이메일·URL·다른 브랜드명 금지.** 브랜드 표기는 "특허그룹 디딤" 하나. 상담 안내(roh@didimip.com)는 본문 CTA만 맡는다.
- **결과 보장·단정 표현 금지**(변리사 광고 규정): "6천만 원 절감합니다", "100% 등록", "무조건" ✗ → "약 6천만 원 줄인 사례", "요건 충족 시 가능" ✓. 사례 수치면 주석에 "개별 상황에 따라 다름".
- 기관명은 '특허청'이 아니라 **'지식재산처'**(2025.10 승격). 과거 서술만 "당시 특허청(현 지식재산처)".
- **디딤 다이어리에는 인포그래픽·CTA를 넣지 않는다.** 분위기 사진만, 사진에 글자·로고 금지.
- **이미지 속 숫자는 본문에 같은 표기로 있어야 한다.** 없는 숫자를 만들거나 반올림하지 않는다.

## 언제 쓰나

- 초안(didim-blog-writer 결과)이나 사용자가 붙여넣은 본문에 썸네일·도표 이미지가 필요할 때
- 기존 글의 이미지만 다시 만들 때, 이미지 마커·ALT 텍스트를 정리할 때
- 쓰지 않을 때: 본문 작성 자체(→ didim-blog-writer), 발행용 복사 텍스트·태그(→ didim-blog-publish-prep)

## 입력

| 항목 | 필수 | 비고 |
|---|---|---|
| 완성 본문 | 필수 | 마크다운/텍스트. 문단 ID(`<!-- p:N -->`)가 있으면 그대로, 없으면 3단계에서 주입 |
| 카테고리 | 필수 | 신규·레거시 이름 또는 네이버 categoryNo. 모르면 사용자에게 묻는다 |
| 핵심 키워드 | 권장 | ALT 앞부분에 넣는다 |
| 글 제목 | 권장 | 썸네일 문구의 재료 (제목을 그대로 옮기지는 않는다) |

| 출원·심판 실무 (27) | 현장 수첩 | 2~3개 (부족 시 1개) | B, D, E |

## 절차

### 1단계 — 카테고리 판별
`scripts/categories.py`로 group(field/lounge/news/diary)을 확인한다. **diary면 6-D(분위기 사진)로 바로 간다.** 설계 단계를 실행하지 않는다.

### 2단계 — 시각화 후보 찾기
본문을 처음부터 끝까지 읽고 아래 중 하나 이상을 만족하는 데이터만 후보로 적는다(개수를 채우려고 약한 데이터로 만들지 않는다).
- 비교할 숫자 쌍(적용 전/후, A안/B안) → A
- 3단계 이상 절차 → B / 핵심 수치 3~4개 → C / 날짜·기간 3개 이상 → D
- 요건·조건 5개 이상 → E / 단계별 수치 3개 이상 → F / 주체 3개 이상과 관계 → G / 같은 단위 수치 3~6개 → H

### 3단계 — 개수·유형·위치 결정
- 썸네일 T 1개 + 본문은 위 표의 범위 안. 같은 유형은 한 번만, **B와 F는 함께 쓰지 않는다.**
- 본문 인포그래픽은 그 데이터를 설명하는 **문단 바로 뒤**(`p:N`). 이미지 사이에 **문단 2개 이상**(썸네일 뒤 첫 이미지는 p:2 이후).
- CTA 바로 앞에는 요약형(A 또는 C)을 권장하되 데이터가 없으면 생략.
- 문단 ID가 없으면 먼저 넣는다(빈 줄로 나뉜 문단마다 1부터): `python3 scripts/insert_markers.py --body body.md --inject-ids > body_ids.md`
  이후 설계·검사·마커 삽입은 모두 이 `body_ids.md` 하나로 한다(ID를 다시 주입하면 번호가 바뀌어 position이 어긋난다).

### 4단계 — 설계 JSON 작성 (이미지마다 8항목)
설계 프롬프트 전문은 `references/design-prompt.md`. Claude가 직접 그 지시를 따라 JSON 배열을 만든다.

| 항목 | 규칙 |
|---|---|
| `type` | T 또는 A~H |
| `position` | 썸네일 "top", 나머지 "p:N" |
| `headline` | 20자 이내(공백 포함). 데이터 이름이 아니라 독자가 얻는 메시지. 광고 규정 준수 |
| `texts` | 이미지에 들어갈 **모든 글자**. 여기 없는 글자는 그리지 않는다. 배치 순서는 아래 표 |
| `data_source` | texts의 수치가 나온 **본문 문장을 그대로** 인용 (썸네일은 `[]` 가능) |
| `emphasis` | texts 안의 값 1~2개 (강조색으로 칠함) |
| `footnote` | 출처(법률·기관)·기준일·단위. 사례면 "개별 상황에 따라 다름" |
| `alt` | 20~40자, 핵심 키워드를 앞에. 같은 키워드를 글 전체 ALT에서 3번 넘게 반복하지 않는다 |

**texts 배치 순서 (render.py가 이 순서로 그린다)**

| 유형 | texts | 비고 |
|---|---|---|
| T | `[카테고리 태그, 메인 줄1, 메인 줄2, (줄3), (서브문구)]` | 메인 한 줄 6~9자(최대 10자), 2~3줄. 11자 이상 항목은 서브문구(12~18자, 1개) |
| A | `[라벨A, 값A, 라벨B, 값B, (차이)]` | 위아래 2단 + 가운데 차이. 값이 같은 단위면 비율 막대 자동 |
| B | `["제목|설명", ...]` 3~5개 | `|` 뒤 설명은 선택 |
| C | `[라벨, 값, 라벨, 값, ...]` 3~4쌍 | 3쌍=세로 3칸, 4쌍=2×2 |
| D | `[시점, 내용, ...]` 3쌍 이상 | 시간 순으로 |
| E | `[항목, ...]` 5~7개 | 한 줄 항목 |
| F | `[단계, 수치, ...]` 3쌍 이상 | 넓은 단부터 |
| G | `[중심 주체, "주체|관계", ...]` | 주변 주체 2~6개 |
| H | `[라벨, 값, ...]` 같은 단위 3~6쌍 | 큰 값부터 자동 정렬 |

C·D·F·H에서 짝이 안 맞아 남는 마지막 항목은 하단 요약 문구로 그린다. `|`는 구분자라 그려지지 않는다.

**썸네일 문구 요령**: 제목을 그대로 옮기거나 "N가지", "완벽 가이드" 같은 제목 공식을 쓰지 않고 독자의 질문·상황으로 바꾼다. 예) "벤처인증 / 유형 잘못 고르면 / 생기는 일". 가장 중요한 단어나 숫자 하나만 `emphasis`.

### 5단계 — 검사
```
python3 scripts/check_sources.py --design design.json --body body.md --category "<카테고리>" --keyword "<키워드>"
```
- data_source가 본문에 그대로 있는지, headline·texts·footnote의 모든 숫자가 본문에 같은 표기로 있는지, 글자 수·강조·광고 규정·연락처·'특허청'·이모지·ALT·개수·중복·B+F·이미지 간격을 검사한다.
- **errors가 0이 될 때까지 설계를 고친다.** 숫자가 본문에 없으면 숫자를 지우거나 본문 표기로 바꾼다(본문을 몰래 고치지 않는다 — 본문 수정이 필요하면 사용자에게 알린다). warnings는 판단해서 고치거나 이유를 남긴다.

### 6단계 — 렌더링
```
python3 scripts/render.py --input design.json --category "<카테고리>" --out out/ --png auto
```
- 표준 라이브러리만으로 SVG를 만들고, `cairosvg` → Python `playwright` → Node `playwright` 순으로 PNG 변환을 시도한다. 없으면 SVG + `preview.html`만 준다(사용자가 브라우저에서 열어 저장).
- 결과 JSON의 `warnings`(줄 넘침·글자 축소 등)와 `font_note`를 확인한다. 'Noto Sans KR'이 없으면 대체 폰트로 그려져 줄바꿈이 조금 달라질 수 있다고 알린다.
- 크기: 썸네일 1080×1080, 본문 1080×1350. 가장 작은 글자 28px(폭의 2.5%) 이상을 스크립트가 지킨다.

### 6-D — 다이어리 분위기 사진 (다이어리만)
설계 JSON을 만들지 않는다. 사진 1~2장(4:3, 1080×810)을 위해: ① 실제 사무실·현장 사진을 먼저 권한다. ② 없으면 아래 형식으로 이미지 모델용 프롬프트를 준다(글자·로고·사람 얼굴 없음).
```
[분위기 사진 N] 위치: p:N 뒤 / 장면: <예: 새벽 사무실 불빛>
ALT: <20~40자>
English prompt: A quiet, natural-light photograph of <scene> in a small Korean patent law office.
Documentary style, soft colors, 4:3 aspect ratio. No people's faces, NO text, no letters, no logos, no signage in the image.
```
장면 예(원본 코드의 12개): 사무실 창밖 석양, 커피와 노트북, 회의실 화이트보드, 비 오는 날 카페 창가, 책상 위 특허 서류 더미, 팀 회식 풍경, 출장길 KTX 차창, 주말 공원 산책, 새벽 사무실 불빛, 고객사 방문 후 귀갓길, 세미나장 풍경, 연말 정리하는 책상.

### 7단계 — 직접 보고 고치기
PNG가 있으면 1~2장 이상을 직접 열어(이미지 보기) 겹침·잘림·외톨이 글자를 확인한다. 문제가 있으면 **texts를 줄이거나 짧은 표현으로 바꿔** 다시 렌더링한다(글자를 작게 만들지 않는다).

### 8단계 — 본문에 마커 넣기 (선택)
```
python3 scripts/insert_markers.py --body body_ids.md --design design.json > body_with_markers.md
```
레거시 `━━ 📷 이미지 N ━━ / [IMAGE: … ]` 마커 형식으로 위치에 넣는다(발행 준비 스킬이 이 마커를 읽는다). 설계 객체에 `"file": "01_A.png"`를 넣으면 마커에 파일명이 남는다.

### 9단계 — 발행 전 검수 체크리스트 (모두 ✓여야 완료)
- [ ] 이미지 속 수치가 모두 본문에 같은 표기로 있다
- [ ] 결과를 보장하는 표현이 없다
- [ ] 썸네일 한 줄이 10자를 넘지 않고, 모바일 크기로 줄여도 읽힌다
- [ ] "특허그룹 디딤" 외에 연락처·URL·다른 브랜드가 없다
- [ ] 색이 팔레트 밖에서 나오지 않았다
- [ ] 이미지가 연속으로 붙어 있지 않다(사이 문단 2개 이상)
- [ ] 이미지마다 ALT 텍스트가 있다
- [ ] 기관명이 '지식재산처'로 되어 있다

## 출력 형식

사용자에게 아래 순서로 준다.
1. **설계 요약 표**: 번호 / 유형 / 위치(p:N) / 헤드라인 / ALT
2. **설계 JSON** (코드 블록, 재렌더링용)
3. **검사 결과**: 오류 0 확인, 남은 경고와 판단
4. **이미지 파일**: PNG(가능하면) 또는 SVG + preview.html 경로. 다이어리는 사진 프롬프트
5. **검수 체크리스트** 결과
6. (요청 시) 마커가 들어간 본문

### Notion 기록 — 글 페이지 `## 인포그래픽` 섹션 (_DECISIONS.md 7절)
Notion "디딤 블로그 콘텐츠"(data source `collection://463bc815-11ab-4290-9d86-22bd1aa9cfed`)에 그 글의 페이지가 있으면, 위 1번 **설계 요약 표**를 페이지 본문 `## 인포그래픽` 섹션에 둔다. '메모' 열은 사람 전용이라 쓰지 않는다. 섹션 형식은 didim-blog-core `references/notion-storage.md` 3절.
1. `python3 scripts/notion_page.py infographic-section --design design.json > infographic.md` → Notion 표(`<table>`): 번호 / 유형(T 썸네일, A 비교 …) / 위치(top, p:N) / 헤드라인 / ALT. 다이어리는 사진마다 `{"type":"사진","position":"p:N","scene":"<장면>","alt":"<ALT>"}` 배열로 같은 명령을 쓴다(헤드라인 칸 = 장면).
2. 페이지를 notion-fetch 해 `page.txt`로 저장 → `python3 scripts/notion_page.py section --page-file page.txt --name 인포그래픽 --content-file infographic.md` 결과를 notion-update-page(`update_content`)에 그대로 넘긴다(사용자 확인 후). 다른 섹션(본문·발행 블록 등)은 건드리지 않는다. 다시 설계하면 같은 명령으로 덮어쓴다.
3. writer 흐름 안에서 아직 페이지가 없으면 `infographic.md`를 writer에 넘긴다(writer가 페이지를 만들 때 `## 인포그래픽`에 넣는다).
4. 커넥터가 없으면 설계 요약 표를 그대로 보여 주고 붙여넣기를 요청한다.
이미지 파일 자체는 Notion에 올리지 않는다(네이버에 직접 올림). 마커 삽입 본문으로 `## 본문`을 바꿔야 하면 writer 흐름(또는 사용자 확인 후 `section --name 본문 --code markdown`)으로 한다.

## 금지·주의

- texts에 없는 글자, 이모지, 아이콘 글자(📋 등)를 이미지에 넣지 않는다. 아이콘이 필요하면 도형으로만.
- 썸네일에 수치 비교표·체크리스트·절차 도식을 넣지 않는다(본문 인포그래픽으로).
- 한글이 들어간 인포그래픽을 이미지 생성 모델에 맡기지 않는다(숫자·조문 한 글자 오류 위험). 이미지 모델은 다이어리 사진·배경 일러스트에만, "NO text"로.
- 감정 톤으로 색을 바꾸지 않는다. 감정은 헤드라인 문구로 표현한다.
- 본문에 없는 수치를 이미지용으로 만들지 않는다. 추정치는 본문에 "약" 또는 "(E)"가 있어야 이미지에도 쓴다.
- 네이버 자동 업로드를 하지 않는다. 사용자가 이미지 파일을 직접 올린다.
